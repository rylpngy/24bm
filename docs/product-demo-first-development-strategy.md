# 产品可演示优先研发策略

## 核心调整

从现在开始，项目研发方式调整为：先完成可演示业务闭环，再补工程质量。

此前项目已经沉淀了大量 Java 后端能力、状态机、审计、附件、财务、合同和测试脚本，但这些工作对浏览器里的产品效果提升不够直接。后续研发必须先让采购方主流程在页面上可看、可讲、可操作，再逐步补测试、抽组件和后端边界。

## 当前优先级

第一优先级只保留一条采购方演示主线：

采购需求 → 审批中心 → 询价项目 → 报价对比 → 采购订单 → 收货验收 → 发票付款

这 7 个页面要先达到以下效果：

- 页面能讲清楚业务状态、下一步动作和不可操作原因。
- 关键按钮和状态反馈能支撑演示，不让用户猜系统当前在干什么。
- 列表、详情、操作区的视觉层级清楚，避免页面像数据堆叠。
- 主流程能从一个页面自然跳到下一个页面。
- Java 数据源下页面稳定可打开，不出现加载失败、空白页或明显运行时错误。

## 执行规则

- 暂停扩展新模块：不继续新增商城、竞价、招标、AI、复杂合同、复杂财务归档或 ERP 集成。
- 每轮只交付 1 到 2 个页面的可见改进，优先让用户在浏览器里看到变化。
- 不再以自动化视觉脚本作为主要推进方式；脚本只作为辅助验收，不再让脚本等待和截图流程主导开发节奏。
- 测试策略从“全覆盖优先”调整为“关键演示路径保护优先”：只为本轮页面主动作、关键状态和容易回归的逻辑补轻量测试。
- 后端质量仍保留，但只有当演示路径需要真实保存、真实状态流转或真实错误反馈时才补后端。
- `App.tsx` 暂时允许小步改动，但连续两轮修改同一区域后必须考虑抽出局部组件，避免继续膨胀。

## 阶段七页面顺序

1. 采购需求 + 审批中心：先把需求申请、提交审批、审批通过/驳回的演示体验打通。
2. 询价项目 + 报价对比：把创建询价、供应商邀请、报价比较、推荐定标和订单后只读状态讲清楚。
3. 采购订单 + 收货验收：把订单履约、供应商确认、发货、到货、验收登记做成清楚的时间线。
4. 发票付款：把发票、三单匹配、付款状态、付款登记边界整理成可演示台账。
5. 最后再做整体视觉统一、移动端修整和必要的 Java 回归验证。

## 不再继续的做法

- 不再连续多轮只新增后端类、迁移、测试和文档，而页面没有明显变化。
- 不再一次性铺开多个业务域。
- 不再把“测试通过”当作“产品可用”的替代。
- 不再让长时间运行的视觉自动化脚本阻塞页面体验迭代。

## 验收标准

每一轮结束时，只回答三个问题：

1. 用户打开页面能不能明显看到改进？
2. 采购主流程是不是比上一轮更容易演示？
3. 当前页面的状态、动作和限制是不是能被业务人员理解？

只有这三个问题都能回答“是”，才算本轮真正有效。
