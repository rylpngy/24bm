## 5 分钟讲解节奏

### 0:00 - 0:40 开场定位

这一页演示的是阶段十三合同深化，不是完整法务合同系统。合同管理在当前采购 SaaS 里的定位是：采购订单形成后，采购方把订单沉淀为合同台账，再围绕合同审批、履约事件、收货验收、发票付款和归档门禁做可演示的业务闭环。

现场话术：

合同页不是孤立的合同列表，而是采购订单之后的履约管控入口。它把订单、审批、收货、发票付款和归档证据聚合到同一个业务视角里，方便采购负责人判断下一步该做什么。

### 0:40 - 1:30 合同总览

先看合同总览和阶段十三合同深化面板。这里用 `stage13-contract-demo-readiness` 讲七件事：

- 合同总览：当前有多少合同、草案、生效/履约和已归档。
- 合同审批：合同能进入审批中心，不和需求审批、定标审批割裂。
- 履约事件：收货和付款可以沉淀为合同履约证据。
- 订单/收货/发票/付款关系：合同聚合关系，但不替代这些模块。
- 归档门禁：归档必须满足审批、附件、履约事件和付款等前置条件。
- 演示操作条：真实按钮集中在合同详情第一屏。
- 推荐合同样本：现场优先讲稳定样本，不临时找数据。

现场话术：

这块面板是给演示者和业务方看的地图。我们先告诉客户这页能讲什么、哪些动作是真按钮、哪些事情现在只是边界说明，避免把合同深化讲成大而全的法务系统。

### 1:30 - 2:40 五个真实动作

打开推荐合同样本后，进入合同详情第一屏，重点讲 `stage10-contract-demo-action-loop`。

1. 提交合同审批：点击后合同进入审批中心，说明合同审批和采购方内控队列打通。
2. 推进履约：把合同状态推进到履约完成，说明合同状态能跟随业务推进。
3. 处理收货验收：跳转收货验收页，保留合同上下文。
4. 处理发票付款：跳转发票付款页，保留合同上下文。
5. 归档合同：只有满足归档门禁时才允许提交 Java 服务端校验。

现场话术：

这里不是放一排展示按钮，而是五个可以解释业务结果的真实动作。每个按钮都对应一个采购业务节点：审批、履约、收货、付款和归档。按钮不可点时，也会通过状态和原因说明为什么不能点。

### 2:40 - 3:30 关系解释

重点说明合同不替代订单、收货、发票和付款模块。

- 订单仍然负责供应商、金额、履约和预计到货。
- 收货验收仍然负责到货确认和异常记录。
- 发票付款仍然负责对账、付款状态和付款审计。
- 合同负责把这些结果聚合成履约和归档证据。

现场话术：

合同不是另一个订单，也不是另一个付款模块。合同页的价值是把这些模块产生的证据串起来，让采购方知道合同现在是否能继续履约、是否还有风险、是否可以归档。

### 3:30 - 4:20 归档门禁

归档合同是收口动作，也是风险边界。演示时不要只讲“能归档”，要重点讲“为什么现在不能归档”。

归档门禁要讲四类证据：

- 审批是否完成。
- 合同附件或凭证是否登记。
- 收货和付款履约事件是否覆盖。
- 目标对象审计记录是否可追溯。

现场话术：

归档不是把合同状态改成结束，而是一次风险复核。没有满足条件时，系统要告诉采购方缺什么、去哪处理、处理后怎么回到合同页复核。

### 4:20 - 5:00 收口

阶段十三合同深化的演示结论：

合同管理已经从阶段十的“能承接订单演示路径”，推进到“客户可以单独看合同页并理解合同总览、审批、履约、关联单据和归档门禁”。这一轮仍然坚持产品可演示优先，本轮不新增合同工作流接口，而是把已有 Java 数据源、真实按钮和视觉验收证据整理成可讲、可点、可复验的演示切片。

## 客户提问兜底

**问：现在能电子签章吗？**

答：本阶段不声明电子签章。现在先把合同台账、审批、履约、归档门禁这条采购内部管理链路跑通，后续可以接签章平台或法务合同系统。

**问：合同审批是不是完整法务审批？**

答：当前是采购方内控审批演示能力，能进入统一审批中心。多级会签、法务红线、版本对比和条款结构化审查不在本轮范围内。

**问：合同能自动付款吗？**

答：不能。当前只登记付款状态和审计留痕，不触发真实支付。合同页只聚合发票付款结果，不替代付款模块。

**问：为什么归档合同按钮不可点？**

答：归档要满足门禁。通常是审批、附件、履约事件、付款或审计证据还没齐。演示时按页面提示说明缺口，并跳转到对应模块处理。

**问：如果现场数据状态已经变化怎么办？**

答：优先讲推荐合同样本。如果按钮不可用，就讲按钮旁边的状态、动作反馈和下一步承接；需要重新生成证据时运行 `node scripts/stage-thirteen-contract-visual-acceptance-check.mjs` 复跑。
