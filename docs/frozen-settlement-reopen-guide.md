# 跨年冻结订单与补充清算

## 业务边界

本批支持有效项目、未关闭分包下的跨年冻结订单清算，以及已完成清算后的补充清算。补充清算是新协议、新单据、新供应商确认及新独立审批，不修改上一版清算，不恢复履约、不重新发货、不重复释放库存。

不开放已结项/终止项目、已关闭分包的重开；草案撤销、含补偿款的历史清算及存在无法核验的负向付款历史，仍须单独设计处理。不得向未知历史流水补造资金归属。这里的年度是预算责任年度，不等于银行流水发生日期或会计账期。

## 跨年冻结订单

1. 完成原项目的真实跨年承接审批。原付款及承接快照保留，仅未付责任进入目标年度。
2. 在订单的“合同解除与订单清算”中上传双方协议，核对已履行数量、清算单价、逐票最终货款。跨年订单必须明确每张发票/未开票款项的最终归属，即使只有一张发票也不自动分摊。
3. 供应商确认后由采购方提审，沿用独立 Flowable 清算流程，发起人不能自行审批。
4. 审批通过后登记退款凭证，选择发票/款项及原实际付款的责任年度。不能把历史冻结款默认记入当年；退款不能超过该发票、该年度的已付净额。
5. 对专项历史退款，填写原资金来源的实际退款额，并为每个原来源显式选择项目当前方案中的当年责任回补来源。退款现金记回原年度、原来源、原版本；另追加当年责任回补记录，不把回补伪装成当年现金流入或资金划转。
6. 当年回补来源必须为已批准、同部门、当前责任年度、当前方案内的来源，且有足够可用额度；额度不足时先调整额度再申请清算，不自动扩大额度。清算期间相关来源额度和项目责任调整受保护。
7. 补付款只允许使用当前责任年度的来源。完成最终发票/红冲及必要凭证核对后，逐票净额一致才能完成清算。

## 已完成清算后的补充协议

1. 条件满足时，订单显示“发起补充清算”。填写新协议、原因、清算单价及逐票最终货款，提交给供应商确认。
2. 系统绑定当前已完成清算的版本，防止引用其他订单、过期版本或同时产生多个有效分支；相同提交编号按原内容幂等处理。
3. 重新经过供应商确认、采购方提审、独立审批，再登记本次差额退款/补付及最终发票。不得沿用上一版审批直接办理新现金。
4. 本次已付基数为上次清算后的真实净款，包含未开票货款，不再误用最初付款总额。本次目标金额不超过原订单及原履行范围，不能借重开增加采购数量或恢复终止的实物责任。
5. 新协议尚未完成时保留上一版已完成清算口径；在审增额责任受预算校验和占用保护。默认预警模式不变，不能通过重开绕过严格预算模式。
6. 完成后只有最新有效清算计入订单、预算和执行汇总，但全部历史单据、审批、凭证和原归档仍保留。详情可“查看上次清算”；退回或撤回新申请不会改写旧单。

## 查询与归档

凭证显示责任年度，专项来源明细显示当年责任回补目标。内部资金信息仍按预算查看权限和数据范围控制，供应商不返回采购方内部资金快照。

执行档案保留原付款、原归属、历次清算、上下版本关系、真实办理人、现金责任年度及专项回补流水。新归档不覆盖旧 ZIP，旧包可继续下载；项目终止以最新净付保留责任，释放剩余责任，不重复累计多版清算。

本批不自动执行银行转账、银行退款、税控红冲或会计记账，仍需真实凭证核验。

## 隔离验收复跑

在原库备份的恢复副本启动 API `127.0.0.1:8097`、采购方预览 `127.0.0.1:5201`，不能指向原系统端口。先用 `scripts/project-packages-acceptance.mjs` 的 `PROJECT_FUNDING_ACCEPTANCE=1` 等既有联调参数生成隔离的 `fundingUi` 场景，再运行：

```sh
ACCEPTANCE_LOCAL_WRITES=1 \
ACCEPTANCE_PASSWORD='<隔离验收账号密码>' \
FROZEN_SETTLEMENT_FIXTURE='<基础验收报告路径>' \
ACCEPTANCE_REPORT_PATH='<本批结果JSON路径>' \
node scripts/frozen-settlement-reopen-acceptance.mjs
```

脚本建立独立测试企业及场景，不使用已有真实业务单据；执行跨年退款、当年补付、两次供应商及独立审批、桌面/手机页面操作、原数据核对及前后 ZIP 下载比对。不得将验收库覆盖原库；合并和发布仍以 CI、依赖 PR 及最新备份验证结果为准。
