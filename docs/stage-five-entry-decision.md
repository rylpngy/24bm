# 阶段五入口决策

## 决策结论

阶段四财务最终收口包已经把付款前控制、付款批次、执行登记、归档冻结和归档异常收束为可演示基线。阶段五不建议直接进入真实支付，也不建议同时铺开商城、竞价、招标和 AI。

推荐方向：合同管理 MVP。

备选方向：供应商绩效基础评分。

暂不优先：真实支付前置设计。

## 方向对比

| 方向 | 价值 | 风险 | 当前判断 |
| --- | --- | --- | --- |
| 合同管理 MVP | 承接定标、订单、供应商、履约和财务，是采购闭环的自然延伸 | 需要新增合同台账、审批和履约状态，但不涉及外部资金接口 | 推荐作为阶段五第一主线 |
| 供应商绩效基础评分 | 可复用报价、交付、质量、响应和财务异常数据，帮助供应商管理沉淀评分 | 评分口径容易争议，需要先保持透明和可解释 | 适合作为合同 MVP 后的第二主线 |
| 真实支付前置设计 | 可继续深化财务域，补凭证、幂等、回单和异常恢复 | 合规、权限、银行接口、失败重试和资金状态风险最高 | 暂不优先，只保留设计入口 |

## 推荐方向：合同管理 MVP

合同管理 MVP 的目标不是一次性做完整法务合同系统，而是先补采购业务主流程里的合同台账和履约连接点。

第一轮建议：合同管理 MVP 信息架构。

阶段五第一条主链路建议为：采购订单 → 合同草案 → 合同审批 → 合同生效 → 履约跟踪 → 合同归档。

第一轮先落以下范围：

- 合同台账：合同编号、合同名称、采购方、供应商、关联订单、合同金额、合同状态、签订日期、生效日期、到期日期。
- 合同审批：先复用单级审批模型，支持草案提交审批、审批通过、审批驳回和审批摘要。
- 合同履约跟踪：从订单、收货、发票付款派生履约进度，不自动改写订单或财务状态。
- 合同归档：合同完成后进入只读归档，后续修改通过变更申请设计承接。
- 合同附件：先挂接已有附件中心能力，支持合同正文、补充协议和履约附件的关联入口。

## 备选方向：供应商绩效基础评分

供应商绩效基础评分适合在合同 MVP 后进入，因为合同能提供更稳定的履约周期和评价对象。

第一轮可先做透明评分，不做黑盒模型：

- 报价维度：报价参与率、报价及时率、报价有效率。
- 交付维度：准时发货、准时收货、延期次数。
- 质量维度：验收通过率、退回复核、异常记录。
- 协同维度：响应速度、订单确认及时率、发票提交及时率。
- 风险维度：黑名单、归档异常、付款阻断关联记录。

评分结果应支持查看计算依据，不直接自动改变供应商准入、分级或黑名单状态。

## 暂不优先：真实支付前置设计

真实支付前置设计暂不作为阶段五第一主线。原因是当前系统仍明确不接真实支付、银企直连、批量付款执行、税控开票或银行回单。

如果后续进入真实支付前置设计，应先做以下设计，不直接对接银行：

- 付款凭证模型。
- 幂等号和重复提交保护。
- 支付权限和审批权限拆分。
- 支付失败重试和人工恢复。
- 银行回单与平台内付款登记的差异处理。
- 资金状态、平台状态和审计状态的边界。

## 不进入范围

阶段五第一轮先不进入商城、竞价、招标和 AI。

原因如下：

- 商城直采需要商品、协议价、购物车和快速下单规则，会改变采购入口。
- 竞价和招标需要新的交易规则、截标、评审和合规边界。
- AI 需要稳定数据闭环和指标口径，否则容易把建议包装成确定性决策。
- 真实支付仍涉及高风险外部接口和资金状态，不适合与合同管理并行启动。

## 下一步建议

阶段五下一轮建议进入合同管理 MVP 信息架构，先做产品层和前端后台入口规划，再决定是否新增 Java 合同台账。

建议下一轮拆成：

1. 合同管理信息架构：采购方菜单、合同台账、合同详情、审批入口、履约摘要、归档边界。详见 `docs/stage-five-contract-information-architecture.md`。
2. 合同数据模型草案：合同、合同附件、合同履约节点、合同审批任务和审计动作。
3. 前端列表雏形：先接 mock/派生数据，明确页面结构和操作边界。
4. Java 台账设计：在页面和数据字段稳定后再新增合同表、Mapper、Service 和 Controller。
