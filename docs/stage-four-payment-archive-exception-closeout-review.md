# 阶段四付款归档异常收口复盘

## 验收结论

第82轮到第89轮已经把付款批次归档后的异常处理，从“只读申请入口设想”推进到“申请台账 -> 审批任务 -> 审批回写 -> 受控处理 -> 关闭复核 -> Java smoke 回查”的阶段性闭环。

本次复盘覆盖归档异常申请入口、付款归档异常申请 Java 台账、付款归档异常申请审批任务化、付款归档异常审批结果回写、付款归档异常受控处理入口、付款归档异常关闭复核和付款归档异常 Java smoke 闭环。

本轮复盘结论是：系统现在已经具备对已归档付款批次发起异常申请、纳入审批、登记受控处理并完成关闭复核的可验收雏形。完整链路为：已归档付款批次 → 提交归档异常申请 → 审批通过 → 登记受控处理 → 关闭复核 → 台账回查。

需要继续明确的是，这仍然是归档后异常申请台账闭环，不直接解冻或改写已归档付款批次；系统也不接真实支付、银企直连或批量付款执行。

## 已完成能力

- 第82轮 归档异常申请入口：采购方已归档付款批次详情新增归档异常申请入口和 API 草案，支持撤销申请、异常解冻的申请语义，但入口只进入审批台账。
- 第83轮 付款归档异常申请 Java 台账：新增 `payment_archive_exception_requests` 表、领域对象、Mapper、GET/POST 端点和 `payment_archive_exception.requested` 审计，服务层校验目标付款批次必须已归档。
- 第84轮 付款归档异常申请前端提交联动：前端归档异常入口接入 Java POST，提交后刷新采购方数据并在归档异常申请台账回显申请人、申请时间、异常原因和审批状态。
- 第85轮 付款归档异常申请审批任务化：归档异常申请接入审批中心，新增 `payment_archive_exception` 审批业务类型和 `TPL_PAYMENT_ARCHIVE_EXCEPTION` 默认模板，申请创建后生成待审批任务。
- 第86轮 付款归档异常审批结果回写：新增归档异常申请审批端点，审批通过或驳回会回写申请台账和审批任务状态，并记录通过或驳回审计。
- 第87轮 付款归档异常受控处理入口：审批通过的归档异常申请可登记受控处理动作，回写 `action_status/action_result/handled_by` 并写入 `payment_archive_exception.action_completed` 审计。
- 第88轮 付款归档异常关闭复核：受控处理已登记的归档异常申请可关闭复核，回写 `closure_status/closure_result/closed_by` 并写入 `payment_archive_exception.closed` 审计。
- 第89轮 付款归档异常 Java smoke 闭环：`npm run java:smoke` 已覆盖已归档付款批次提交归档异常申请、审批通过、登记受控处理、关闭复核和台账状态回查。

## 收口边界

本轮收口的是“付款批次归档后的异常申请台账闭环”，不是归档撤销、批次解冻或真实资金执行系统。

明确边界如下：

- 只能对已归档付款批次提交归档异常申请，未归档批次仍不允许走该异常入口。
- 审批通过只代表归档异常申请被批准，不代表付款批次已解冻、已重开或已取消归档。
- 登记受控处理只记录人工处理动作和结果，不自动编排付款申请、三单匹配、差异处理、执行记录或付款批次状态。
- 关闭复核只关闭归档异常申请台账，不直接解冻或改写已归档付款批次。
- 不接真实支付、银企直连或批量付款执行，也不提供银行回单、税控开票或外部财务系统同步。
- 当前审批仍是单级审批任务，尚未做多级审批、会签、审批流可视化配置或归档异常权限矩阵。

## 待补强

- 归档异常当前只形成申请、审批、受控处理和关闭复核台账，尚未真正提供归档撤销、异常解冻或批次重开动作。
- 受控处理结果尚未联动付款批次、付款申请、执行记录、三单匹配或差异处理状态，需要后续单独设计状态编排规则。
- 归档异常权限仍复用当前采购方与审批任务基础权限，尚未细分财务负责人、审计负责人和平台运营方权限边界。
- 归档异常审批仍是单级任务，尚未接入多级审批、会签、审批意见模板和审批流可视化配置。
- Java smoke 已覆盖主链路，但发布前仍建议补浏览器视觉验收和权限反例验收。

## 下一步建议

建议把阶段四财务域先做最终收口，再决定是否进入真实支付前置设计或新业务域。

优先顺序如下：

1. 阶段四财务最终收口包：把付款前控制、付款批次、执行登记、归档冻结和归档异常统一为可演示范围、边界和验收命令。
2. 归档异常下一步设计：设计归档撤销申请、异常解冻、批次重开、权限矩阵和审计追踪，但仍应避免普通入口直接改写归档批次。
3. 真实支付前置设计：先补付款凭证、幂等号、失败重试、银行回单、支付状态回调和异常恢复模型，再评估银企直连。
4. 批次审批增强：补审批意见、审批历史、驳回路径、多级审批和会签。
5. 新业务域切换评估：若财务域边界稳定，可进入合同管理或供应商绩效；商城、竞价、招标和 AI 不建议与真实支付前置设计同时启动。
