# 商城直采模块设计(可独立部署)

> 定位决策(2026-08-03):**私域为主 + 公开专区**;**同镜像 + 部署形态裁剪**;**引入商品/SKU 层**。
> 目标客户场景:部分企业只要"商城直采"一种采购方式,需要能单独部署、单独售卖。

## 一、现状与差距

| 维度 | 现状 | 差距 |
|---|---|---|
| 商品模型 | `mall_listings`(租户 × 供应商 × 物料 + 单价 + 单位 + 在架状态) | 无商品聚合、无多规格 SKU、无图片/描述、无起订量/阶梯价/交期/库存 |
| 购物车 | 前端 `useState`,刷新即丢 | 无服务端购物车、无收藏 |
| 下单 | 一次性结算 → 按供应商拆单 → 商城锚点 RFQ + 采购订单 | 无收货地址、无发票信息、无订单备注,期望到货写死"下单 +7 天",无结算确认页 |
| 门户 | 公开商城页:品类统计 + 精选商品,协议价需登录 | 无分类目录树、无商品详情页、无搜索筛选排序、不能下单 |
| 运营 | 供应商自主调价与上下架 | 无上架审核、无评价、无售后 |
| 方式配置 | `tenants.enabled_features` + `TenantFeatureApplicationService.requireEnabled` 已存在,仅 `rfq/order/finance` 三键 | 商城/竞价/招标无键位;**前端完全未读**,导航与创建向导硬编码方式清单 |

结论:能力开关的地基已经有了,缺的是方式注册表、键位与前后端一致的门禁;商城本身缺的是商品域与门户。

## 二、三根支柱

### A. 采购方式能力矩阵(M-0,其余切片的前置)

- **方式注册表**(后端代码内单一事实源):方式码、显示名、能力键、关联导航模块、是否在创建向导出现、公开门户可见性。
- **租户开关**落 `tenants.enabled_features`;新增细分键 `method:mall` / `method:compare` / `method:auction` / `method:single-source` / `method:tender`,保留既有 `rfq/order/finance` 作为模块级总开关(向后兼容,不改语义)。
- **后端门禁**:`ProcurementMethodPolicy.requireEnabled(tenantId, method)` 挂在寻源立项、招标立项、商城下单三个应用层入口。关掉的方式,API 直接拒绝——不只是前端藏起来。
- **前端门禁**:新增能力查询端点,导航 `navigation.ts` 与创建向导的方式清单都由它驱动,替换硬编码。
- **平台端**:租户详情把 `features` 从自由文本升级成方式勾选矩阵,开通即生效。

**验收口径**:只开商城的租户,登录后导航里没有询比/竞价/招标,创建向导只剩商城入口,直接调用被关方式的 API 返回业务错误。

### B. 商城域深化

#### 数据模型(新增)

```
mall_categories      平台标准分类 + 租户自定义(tenant_id 可空=平台级),父子树
mall_products        商品聚合:scope(tenant 私域 / public 公开专区)、supplier_id、
                     category_id、名称、品牌、富文本详情、主图、状态(草稿/待审核/在架/下架)
mall_skus            规格单品:product_id、sku_code、规格键值、material_id(映射物料主数据,
                     保住对账与主数据链路)、单位、价格、起订量、步进量、库存(可空=不限)、交期天数
mall_sku_tier_prices 阶梯价:sku_id、起订数量、单价
mall_product_media   商品图集:storage_key(MinIO)、排序
mall_carts /
mall_cart_items      服务端购物车:租户 + 用户维度,跨会话保留
mall_addresses       收货地址簿:收件人、电话、行政区、详址、默认标记
mall_after_sales     售后单:订单行、类型(退货/换货/维修)、原因、附件、状态流
mall_reviews         评价:订单行、评分、内容(可汇入 D-3 供应商信用画像)
```

**私域与公开专区的区分**:`mall_products.scope`。
- `tenant`:租户私域协议价商品,价格按租户隔离,仅本租户可见可买(现状语义延续)。
- `public`:平台标准品,统一定价,任何已认证买家可见可买;未登录只看标价不能下单。

**存量迁移**:一条 `mall_listings` → 一个单 SKU 的 `tenant` 域商品。订单侧只存行项快照(名称/单位/数量/单价),不外键 listing,因此迁移不影响历史订单与对账。

#### 域规则(集中在 `MallOrderPolicy` / `MallListingPolicy`)

- 起订量与步进量:加购与结算双端校验,不靠前端拦。
- 阶梯价:按结算数量落到对应档位,下单价格由服务端重算,不信任前端传价。
- 库存:非空时下单扣减并防超卖;为空表示不限量(服务类商品)。
- 交期:SKU 交期天数 → 订单期望到货日默认值,允许买家改晚不改早。
- 上下架:待审核商品不可加购;在架商品下架后购物车行标记失效而不是静默消失。

### C. 商城门户(标准电商形态)

新增独立前端 `apps/mall-portal`(独立打包,可单独部署):

| 页面 | 内容 |
|---|---|
| 首页 | 分类入口、精选/新品位、公开专区标品;登录后叠加本租户协议价 |
| 分类页 | 左侧分类树 + 筛选(品牌 / 价格区间 / 供应商 / 交期)+ 排序 + 分页 |
| 商品详情 | 图集、SKU 规格切换、阶梯价表、起订量、交期、供应商资质与信用卡片、加购/立即下单 |
| 购物车 | 按供应商分组、数量步进、失效行提示、合计与拆单预览 |
| 结算 | 收货地址、期望到货日、发票信息、订单备注 → 按供应商拆单提交 |
| 我的订单 | 列表/详情/物流/确认收货/售后入口(复用现有订单与履约端点) |

登录复用 Keycloak;未登录可浏览公开专区标价,私域协议价登录后可见(与现状一致)。

### D. 独立部署形态(商城版)

- 一份代码、一个后端镜像;启动参数 `app.deployment.profile=mall|full` 决定注册哪些 controller,方式开关已由 M-0 统一。
- `infra/docker-compose.mall.yml`:postgres + keycloak + minio + app(mall profile)+ mall-portal + supplier-portal(供应商上架用),不起采购全功能三端。
- 迁移链不分叉:同一份 Flyway,商城版只是用不到其余表。
- **不拆微服务**:拆库会带来跨库一致性、重复认证、基础数据同步三笔长期成本,而隔离收益在单体 + 形态裁剪下已经拿到。
