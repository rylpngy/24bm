# 阶段六真实写入能力实施矩阵

## 阶段目标

阶段五收口后，阶段六优先补真实写入能力，不再继续无限叠加前端只读提示。

本阶段的核心目标是把采购主流程从“后台可看、可提示、部分可操作”推进到“关键动作有 Java API、状态流转有服务端边界、页面操作后能刷新回显、验收脚本能覆盖正反路径”。

阶段六第一轮先做实施矩阵，不新增业务代码。矩阵用于判断下一轮应先补哪条链路，避免在采购需求、RFQ、订单、财务和合同之间同时开工。

## 分类口径

| 分类 | 含义 | 验收判断 |
| --- | --- | --- |
| 已有 Java 写入 | 已有 Java API、前端 client、页面入口和刷新回显，至少覆盖一个正向写入路径 | 可进入一致性、表单抽象和反例测试补强 |
| 只有前端入口 | 页面已有按钮、表单或提示，但没有真实 Java 写入或只做页面内状态 | 不能作为真实业务闭环验收 |
| 需要补 API | 业务动作需要服务端落库、审计或状态变更，但当前缺少端点、表或应用服务 | 阶段六应按优先级补 Java 端点和测试 |
| 需要补状态机 | 端点或入口已存在，但状态边界、幂等、驳回、归档、冻结或跨模块约束不足 | 应补服务端状态约束和反例测试 |

## 第一实施泳道：采购需求写入补强

阶段六第一条实施泳道建议选择采购需求，原因是它是整个采购主流程上游，且已有基础 Java 写入能力，适合作为统一写入体验样板。

目标不是重新做需求模块，而是把已有能力收束为可复用模式：

1. 优先从采购需求创建、编辑、提交审批和审批回写开始，梳理页面入口、Java API、服务端状态、审计动作和刷新回显。
2. 补齐需求写入验收矩阵：草稿创建、草稿编辑、提交审批、审批通过、审批驳回、审批中禁止编辑或明确边界、已通过可创建 RFQ。
3. 将错误反馈、忙碌态、禁用态、审批状态提示和下一步动作统一为阶段六样板。
4. 明确采购需求的状态机边界，再把同一套边界迁移到 RFQ、定标和订单。

## 阶段六不进入范围

- 不进入商城、竞价、招标、AI 或真实支付。
- 不并行重构全部模块的详情页和表单。
- 不把前端归档复核提示直接写成已完成的后端复核工作流。
- 不在没有验收矩阵的情况下新增大块 Java 表或端点。

## 下一轮建议

下一轮建议进入采购需求写入补强的验收设计：

1. 新增 `docs/stage-six-demand-write-hardening-plan.md`，列出采购需求创建、编辑、提交审批、审批回写、RFQ 准备的正反路径。
2. 补采购需求 Java/前端契约测试，确认现有 API 和页面入口是否覆盖这些路径。
3. 如现有能力不足，再补最小 Java 状态约束或前端禁用边界。
4. 保持阶段六第一泳道只处理采购需求，不同时改 RFQ、订单、发票付款和合同。
