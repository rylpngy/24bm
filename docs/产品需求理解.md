# 24Bid 产品需求理解（重写基线）

> 生成时间：2026-06-24
> 用途：作为"按《SaaS 管理系统研发标准 v1.1》重新开发"的需求事实源。前端样式完全复刻现有实现，业务能力以本文为准。
> 来源：对现有 backend-java（16 模块）、App.tsx（21k 行）、data/* 与 services/* 的系统性探查。

## 1. 产品定位与核心假设

24Bid 是**多企业采购协同管理 SaaS**，恰好命中标准第一章的全部核心假设：

| 标准假设 | 24Bid 对应 |
|---|---|
| 多租户、多角色 | 平台运营方 + 多个采购企业（租户）+ 多个供应商企业；企业内再分部门与角色 |
| 流程驱动而非 CRUD | 采购主链路由**状态机 + 审批流**构成 |
| 涉及财务/强一致 | 订单、发票、付款、三单匹配、对账 |
| B2B 形态 | 采购方—供应商协同，并发不极端、业务复杂 |
| 需要私有化交付 | 多租户共享库 + tenant_id，天然兼容一库一租户 |

**结论**：本项目就是这份标准的样板场景，重写时标准条款基本可全量套用。

## 2. 三端角色与边界

| 角色 | 身份上下文 | 能力范围 |
|---|---|---|
| **平台运营方** (platform) | userId（无 tenant/supplier） | 租户管理、企业入驻审核、平台公告、运营概览。不介入具体交易。 |
| **采购方企业** (buyer) | tenantId + userId | 采购主流程全链路 + 私域供应商库、物料目录、组织部门、用户角色、审批中心、财务结算。能力最全。 |
| **供应商企业** (supplier) | supplierId + userId | 受邀询价、报价、确认订单、发货、开票、应收对账、企业档案与资质。只能看自己的数据。 |

隔离机制：`TenantContext`（线程本地 tenantId/supplierId/userId）+ `TenantContextFilter`（从 JWT 填充）+ `TenantAccessGuard`（应用服务层强校验）。**这正是标准第八章"逐接口三维度鉴权"的现有实现。**

## 3. 核心业务闭环（采购主链路状态机）

这是整个系统的主线，重写必须 1:1 还原：

```
采购需求            草稿 → 审批中 → 已通过 / 已驳回(回到草稿可重提)
  ↓ (需求已通过才能转询价，且一个需求只能链一个 RFQ)
RFQ 询价            报价中 → 定标审批中 → 已定标 / (驳回回到报价中)
  ↓ (供应商须已准入+有效资质+被邀请才能报价；一RFQ一供应商一报价；截止后锁定)
供应商报价          已提交 → 已锁定 → 已中选 / 未中选
  ↓ (定标审批通过才能生成订单；一个定标只能生成一个订单)
采购订单            待供应商确认 → 待发货 → 已发货 → 已收货
  ↓ (各节点一单一记录：一PO一发货、一PO一收货、一PO一发票)
发货 / 收货         发货须供应商确认后；收货须有"已发货"事实
  ↓ (收货后才能开票；发票金额=订单金额)
发票               待付款 → 部分付款 → 已付款（已付款不可回退）
  ↓ 
付款/三单匹配/对账   发票×订单×收货三方校验；黑名单供应商不可付款
  ↓ (订单主线稳定后)
合同               台账登记 → 审批 → 履约事件追踪 → 归档（与PO 1:1）
```

**关键不变量（数据库唯一约束兜底 + 服务层校验）**：
- `materials (tenant_id, code)`、`buyer_supplier_relations (tenant_id, supplier_id)`
- `rfq_invites/quotes (tenant_id, rfq_id, supplier_id)`
- `deliveries/receipts/invoices (tenant_id, order_id)` 各自唯一
- `contracts (tenant_id, related_order_id)` 唯一（PO↔合同 1:1）

## 4. 模块地图（16 个业务上下文 → 标准三层）

按标准第三章"基础平台 → 主数据 → 核心业务 + 横切"重新归位：

**基础平台层**：`tenant`（租户/功能开关）、`identity`（三端用户/JWT）、`organization`（部门）、`dictionary`（字典）、`platform`（运营）
**主数据层**：`catalog`（物料）、`supplier`（私域供应商关系/资质/公共档案）
**核心业务链路层**：`demand`（需求）、`sourcing`（RFQ/报价/定标）、`order`（订单/发货/收货）、`finance`（发票/付款/批次/三单匹配/对账）、`contract`（合同）
**横切能力**：`approval`（审批模板）、`notification`（站内通知）、`attachment`（附件/版本）、`audit`（审计日志）

> 现有 `buyer` 模块是采购方工作台聚合视图。重写时应明确：聚合查询属于读模型，不应反向耦合业务模块。

## 5. 横切能力（被各层调用，不反向依赖业务）

- **审批**：固定模板触发（需求 `TPL_PURCHASE_DEMAND`、供应商准入 `TPL_SUPPLIER_ADMISSION`、定标 `TPL_RFQ_AWARD`、合同、付款批次等）。**现状是写死的固定模板——重写时这里是接入 Flowable「规则配置式」一期的落点（标准第五章）。**
- **通知**：主流程每个关键节点都发站内通知（需求审批、RFQ 邀请、报价提交、定标结果、订单确认/发货/收货、发票、付款）。
- **附件**：upload-ticket → upload-sink → download-link 三步；owner 多态（demand/rfq/quote/order/invoice/contract/profile）；版本号递增 + 软删除；visibility 控可见范围。**现状 local 存储——重写时换 MinIO（标准）。**
- **审计**：所有关键动作写 `audit_logs`（actor/action/targetType/targetId）。

## 6. 数据规模与 API 面

- **API 端点 ~125 个**：平台 15、采购方 80、供应商 27、共享 2（登录/字典）。前缀 `/api/v1`，Bearer JWT + 租户头。
- **三端 Workspace 聚合读模型**：登录后各拉一个 workspace（buyer 含 tenant/users/departments/suppliers/materials/demands/rfqs/orders/deliveries/invoices/auditLogs/workflow + KPI；supplier 含 opportunities/quotes/orders/deliveries/invoices/qualifications；platform 含 overview/tenants/enterpriseReviews）。
- **数据访问层**现状：`procurementApiClient.ts` 用 `VITE_DATA_SOURCE` 在 mock / java 间切；契约是前端手写 `apiContract.ts` 导出 OpenAPI（**方向与标准相反，重写时改 springdoc 后端生成**）。

## 7. 前端视觉体系（必须原样复刻）

重写前端**完全沿用当前样式**。以下是要保留的设计语言：

### 7.1 布局壳
- 三端共用：左侧 `bg-slate-950` 深色侧边栏（`lg:w-72`，角色分组 + 模块导航）+ 顶栏（工作区标题/搜索/主操作/通知）+ 主内容区（`max-w-7xl` 居中，`bg-slate-100/70`）。移动端侧边栏转顶部导航。
- 采购方导航 12 模块：首页看板、采购需求、审批中心、供应商库、物料目录、询价项目、报价对比、采购订单、合同管理、收货验收、发票付款、审计日志。

### 7.2 设计 token
- 字体 Inter；底色 `#f8fafc`（slate-50/100）。
- 主品牌色 `blue-600/700`；语义色：成功 `emerald-50/700`、警告/进行中 `amber-50/700`、中性 `slate-100/600`、错误 `red-50/700`、信息 `blue-50/700`、演示高亮 `sky-50/300`。
- 统一 `rounded-lg`、`shadow-sm shadow-slate-200/50`、字重偏重（标题 `font-black`，正文 `font-bold`），金额用 `font-mono font-black`。
- **模块色**：需求蓝、询价 indigo、订单 cyan、收货 lime、发票 fuchsia（卡片 hover/选中边框各用自己的色）。

### 7.3 核心组件（约 30 个，重写时作为组件库）
- 基础：`StatusPill`（按中文状态文本自动配色——绿/黄/灰逻辑要原样抄）、`MiniFact`、`InlineFactGrid`、`PrimaryActionButton`（tone+size）、`DetailToggleButton`。
- 容器：`Panel`、`DetailHeroCard`、`DetailSection`、`DetailActionPanel`、`DetailKeyValueRow`。
- 列表：`ListToolbar`（左蓝竖线 + 计数 + 筛选）、`ResponsiveTableFrame`（移动卡片/桌面表格双形态）、各模块 `*ListRowCard`。
- 反馈：`NextActionNotice`、`ProcessStateNotice`（已处理/等待/阻断三态）、`FeedbackNotice`、`ShellState`（loading/empty/error）、`PermissionBoundaryPanel`、`SelectedBusinessHandoffPanel`。
- 页面模式：列表页（Panel + ListToolbar + 筛选 + ResponsiveTableFrame）；详情页（HeroCard + DetailSection×N + ActionPanel + NextAction）；比价矩阵（按 tone 堆叠报价卡，已定标绿/推荐蓝/其他灰）。

> 复刻策略：标准要求迁移到 shadcn/ui + Radix + TanStack Table。落地方式是**用 shadcn 体系重建这些组件，但视觉输出（className 语义、配色、间距、状态色）与现状逐像素对齐**——换的是底层用料，不是观感。

## 8. 重写时与标准的关键对齐点（预告，不在本文展开）

| 现状 | 标准目标（重写采纳） |
|---|---|
| 自研 JWT | Keycloak + Spring Security |
| 固定审批模板 | Flowable 规则配置式（一期） |
| local 附件存储 | MinIO |
| 无 Redis | Redis 缓存/会话 |
| 前端手写契约 | springdoc 后端生成 → orval 前端派生 |
| 单 App.tsx 21k 行、三端同 bundle | monorepo + 运营后台独立 app（platform-admin / tenant-portal） |
| 自研 apiClient | TanStack Query；自绘组件 → shadcn；表格 → TanStack Table |
| 无领域事件 | 跨模块/横切用领域事件解耦 |
| 无 ArchUnit | ArchUnit 守模块边界 |

详细取舍与优先级见 `docs/标准对标差距分析.md` 与 `docs/后续研发路线.md`。

## 9. 范围边界（MVP 内 / 暂缓）

- **MVP 内（重写优先）**：上述采购主链路 + 私域供应商库 + 物料 + 审批 + 三端权限 + 横切四件套。
- **可演示/二期**：合同全生命周期、财务深化（付款批次/三单匹配明细/对账）、平台轻量治理。
- **明确暂缓 (P3)**：商城直采、竞价采购、复杂招标/专家评审、公共供应商市场、AI 寻源、ERP/OA/支付集成、电子签章。
