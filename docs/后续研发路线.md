## 1. 核心策略（以下为 2026-06-24 历史规划，留作背景）

**不做"先改造、再开发"两个串行阶段**，而采用 **"薄地基 + 试点切片 + 边开发边迁移"**（绞杀者模式）：只把"必须先就位、否则新代码一出生就不合规"的东西提前做掉，其余存量代码**只在下次触碰时顺手迁移**，永不为合规而专门重写。

核心取舍：避免出现一个不产生业务价值的纯重构停摆期。

## 2. 判定规则：一项改造现在做 / 碰到才做 / 按需立项 / 不做

| 何时做 | 判据 | 对应项 |
|---|---|---|
| **现在就做**（地基） | ① 安全/正确性问题；② 决定所有未来代码的"形状"，晚做=返工；③ 成本低 | 运营后台隔离、契约方向反转(springdoc)、ArchUnit 护栏、前端 app 拆分骨架 |
| **碰到才做**（绞杀） | 仅是"用错库"的可工作业务逻辑，换库不改逻辑 | TanStack Query 替自研 client、shadcn 替自绘、RHF+Zod、Zustand、TanStack Router |
| **按需立项**（重器） | 当前无真实痛点，引入成本高，需外部驱动 | Flowable、Keycloak、Redis、MinIO |
| **不做** | 标准明确暂缓、MVP 不需要 | 商城 / 竞价 / 复杂招标 / AI |

一句话原则：**改"形状"的现在做，改"用料"的碰到再做，上"重器"的等驱动。**

## 3. 阶段计划

### 阶段 0 · 收口在制工作（0.5–1 天，阻塞项）

- 当前工作区 146 个 dirty 文件（物料状态 V123、附件版本 V124 等）跑 `npm run verify` + 后端 `mvn test`，确认绿灯。
- 修掉迁移跳号 / dev seed 改名带来的 Flyway 问题。
- 提交并补齐对应验收证据。
- **门禁：工作区不清干净不开新工。**

### 阶段 1 · 薄地基（3–5 天，只做"改形状"四件事，不碰业务逻辑）

1. **后端 springdoc**：OpenAPI 从后端注解生成，纠正契约方向（对标 §S1）。
2. **前端 app 拆分骨架**：运营后台从 `App.tsx`（21,040 行）物理切出（安全债，标准第六章点名）；外部门户暂留单 app。先立 monorepo/目录结构，不强制迁页面。
3. **ArchUnit**：守模块依赖方向，防止退化成大泥球（成本极低）。
4. **orval 管道**：从 OpenAPI 自动派生 client/hooks 的流水线跑通一次（哪怕只覆盖一个接口）。

> 杠杆点：这四项完成后，之后写的每一行新代码都自动合规。

### 阶段 2 · 标准对标试点切片（1–1.5 周，首个里程碑）

按 `docs/标准对标差距分析.md` §4 的 S1–S8，把 **"询价→报价→比价"** 链路在新地基上完整重做：
springdoc 契约 + orval hooks + Zod 校验 + TanStack Table 比价矩阵 + 抽成独立模块 + Playwright e2e + 端到端验收文档。

完成后回写差距文档勾选项，并在《研发标准》补"重器引入时机"条款，闭环检验标准本身。

### 阶段 3 · 继续开发剩余功能（绞杀式推进，持续）

在新地基上按既定路线推进；每碰一个老模块就顺手把它的前端迁到新栈：
1. task-39：发票付款页面信息架构与财务台账降噪（台账指定的下一项）。
2. 平台运营轻量治理补强（租户创建、企业审核详情、公告生命周期、功能开关）。
3. 合同订单后置闭环（订单转合同、合同审批、履约事件、归档）。
4. 权限深化（菜单级权限、角色权限点、部门数据权限）。

### 阶段 4 · 重器按需立项（独立排期，不进主线）

由真实驱动触发，不提前做：
- **Flowable**：审批复杂度真的超过固定模板时。
- **Keycloak**：出现企业 SSO 大客户时。
- **MinIO**：附件要上生产时。
- **Redis**：性能 / 会话 / 分布式锁有真实需求时。
