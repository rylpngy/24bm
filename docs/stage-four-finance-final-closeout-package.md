# 阶段四财务最终收口包

## 最终验收结论

阶段四财务域已经形成面向采购方后台的财务协同演示基线，可按“付款前控制、付款批次、执行登记、归档冻结、归档异常”五条主线进行验收。

当前系统能够解释一张发票是否具备付款条件，能从三单匹配异常进入差异处理，能创建和审批付款申请，能汇总付款批次并推进批次审批，能登记平台内付款执行状态，能在全部执行记录已登记后归档付款批次，能在归档后冻结关键写入口，并能对已归档付款批次发起归档异常申请、审批、受控处理和关闭复核。

阶段四最终收口包的产品定位是：采购方平台内的财务协同、付款前控制、付款登记、归档审计和归档异常申请台账，不得误读为真实支付系统。

## 验收范围

| 主线 | 可验收能力 | 验收判断 |
| --- | --- | --- |
| 付款前控制 | 三单匹配、金额差异识别、差异处理台账、差异未处理阻断付款申请、差异处理后恢复付款申请 | 可作为付款前控制基线 |
| 付款批次 | 付款申请台账、单级审批、付款批次台账、批次风险、批次详情、批次审批任务、批次状态动作 | 可作为平台内付款计划与批次管理基线 |
| 执行登记 | 付款执行记录、执行阻断原因、执行汇总、登记前置条件、专用登记入口和登记后复核提示 | 可作为平台内付款登记基线 |
| 归档冻结 | 归档门禁、归档审计摘要、归档后冻结关键写入口、冻结反馈、归档审计面板 | 可作为只读审计闭环 |
| 归档异常 | 已归档批次异常申请、审批任务、审批回写、受控处理、关闭复核和 Java smoke 回查 | 可作为归档后异常申请台账闭环 |

## 演示路径

建议按以下五条路径演示，不建议现场临时扩展到真实付款、银行回单或外部系统。

1. 发票付款 → 三单匹配 → 差异处理 → 付款申请
   展示发票维度的订单金额、收货状态、发票金额、差异金额、匹配结论和付款准备状态；金额差异进入差异处理台账，未处理差异阻断付款申请，处理后恢复付款申请。

2. 付款申请 → 付款批次 → 批次审批 → 执行记录
   展示付款申请创建、提交审批、审批通过、归属付款批次、批次金额、计划付款日、批次风险和批次执行记录。

3. 执行记录登记 → 归档门禁 → 归档审计面板
   展示付款执行记录登记前置条件、专用登记入口、全部执行记录登记后的归档放行、归档前执行摘要和归档审计面板。

4. 已归档批次 → 冻结反馈 → 审计查看
   展示已归档付款批次只允许审计查看，付款申请、差异处理、执行登记和阻断处理写入口被阻断，并把冻结拒绝转成采购方可理解的业务反馈。

5. 已归档批次 → 归档异常申请 → 审批 → 受控处理 → 关闭复核
   展示已归档付款批次可提交撤销申请或异常解冻申请，审批中心生成待审批任务，审批结果回写申请台账，审批通过后登记受控处理，最后关闭复核并回查台账状态。

## 必须保留边界

阶段四最终验收时必须同步说明以下边界：

- 不接真实支付、银企直连、批量付款执行、税控开票或银行回单。
- 登记付款状态只代表平台内状态登记，不代表真实资金划拨完成。
- 已归档付款批次只允许审计查看，不允许付款申请、差异处理、执行登记或阻断处理继续写入。
- 归档异常申请只回写申请、审批、受控处理和关闭复核台账，不直接解冻或改写已归档付款批次。
- 付款阻断处理状态不自动编排付款、三单或差异状态，需要通过现有复核入口显式刷新或定位处理。
- 批次审批仍是单级审批任务，尚未接入多级审批、会签或审批流可视化配置。
- 三单匹配支持手动刷新和历史回填，尚未做定时重算、跨订单匹配或一票多单拆分匹配。

## 待补强

- 归档异常当前只形成申请台账闭环，尚未真正提供归档撤销、异常解冻或批次重开动作。
- 付款执行登记仍是平台内状态流转，尚未引入付款凭证、银行回单、幂等号、失败重试和异常恢复。
- 批次审批仍是单级任务，尚未接入多级审批、会签、审批意见模板和审批历史。
- 归档审计面板尚未提供导出、打印、附件归档或财务凭证关联。
- Java 视觉验收已有 DOM 和截图证据，发布前可再补稳定的可点击性、横向溢出和权限反例验收。

## 下一阶段建议

阶段四按本收口包验收后，下一阶段建议从以下方向选择其一，不建议并行铺开：

1. 付款归档异常设计深化：补归档撤销动作、异常解冻、批次重开、权限矩阵和审计追踪。
2. 真实支付前置设计：补付款凭证、幂等号、权限校验、失败重试、银行回单和异常恢复模型。
3. 批次审批增强：补审批意见、审批历史、驳回路径、多级审批和会签。
4. 新业务域切换：优先合同管理或供应商绩效；商城、竞价、招标和 AI 建议等待财务域边界稳定后再进入。

阶段五入口决策已沉淀到 `docs/stage-five-entry-decision.md`，建议以合同管理 MVP 作为下一轮主线。
