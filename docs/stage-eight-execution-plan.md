# 阶段八演示链路产品化加固计划

## 阶段八目标

阶段八的目标不是继续扩大模块数量，而是把阶段七已经跑通的 `17 个真实点击动作` 做成更像产品、更容易现场演示、更容易让业务人员理解的体验。

阶段七已经证明 Java 数据源下三端主线能跑通：采购方 7 个动作、供应商 5 个动作、平台端 5 个动作。阶段八要解决的是另一类问题：用户打开页面后是否能快速理解当前状态、下一步动作、失败原因、只读边界和操作结果。换句话说，阶段八优先交付用户看得见的业务体验。

## 执行边界

阶段八坚持三条边界：

- 不扩新模块：不进入商城、竞价、招标、AI 或 ERP 集成。
- 不新增复杂后端领域：只有演示链路需要真实保存、真实状态流转或真实错误反馈时，才补 Java 接口或状态边界。
- 不把演示口径包装成生产完成：真实支付、电子签章、生产级权限矩阵、计费套餐、开放 API 和 Webhook 仍然只作为后续生产化范围。

## 工作顺序

| 轮次 | 主题 | 重点页面/角色 | 产出目标 |
| --- | --- | --- | --- |
| 第一轮：三端动作反馈与失败提示 | 围绕 17 个真实点击动作补更明确的操作前提示、操作后反馈和失败兜底 | 采购方、供应商、平台端 | 演示时每个关键按钮都能说明“为什么能点、点完发生什么、失败看哪里”。 |
| 第二轮：只读边界与空状态 | 把不可操作、已完成、已撤回、已归档、无数据等状态做成业务可理解的页面提示 | 采购方 7 页优先，供应商和平台端跟进 | 减少演示时“按钮为什么没有/为什么不能点”的解释成本。 |
| 第三轮：移动端和密度收敛 | 修整三端重点页面在移动端的横向溢出、卡片密度、按钮换行和信息层级 | 三端演示入口与 17 个动作相关页面 | 手机或窄屏演示时不出现明显错位、遮挡和难以点击的问题。 |
| 第四轮：高频组件抽取 | 从 `App.tsx` 抽出重复演示台、状态摘要、操作反馈、详情面板和列表工具条 | 前端共享组件 | 降低后续页面迭代成本，避免继续堆叠单文件复杂度。 |
| 第五轮：权限与审计演示增强 | 让三端动作能在权限说明、审计日志和操作留痕里形成闭环 | 采购方、供应商、平台端 | 演示时能说明“谁可以做、做了什么、系统如何留痕”。 |

## 第一轮建议范围

阶段八第一轮只处理动作反馈和失败提示，不新增业务模块。建议从三端现场演示总验收包里抽出 17 个动作，逐个补三个信息：

| 角色 | 动作范围 | 第一轮要补的体验 |
| --- | --- | --- |
| 采购方 | 提交审批、通过审批、创建询价、提交定标审批、生成采购订单、登记收货、登记付款 | 每个动作旁边显示当前业务前置条件、成功后下一页、失败兜底入口。 |
| 供应商 | 提交报价、确认订单、提交发货、提交发票、保存对账备注 | 明确供应商只能处理自己的邀请、订单和应收记录，并提示采购方驱动的状态边界。 |
| 平台端 | 停用租户、升级专业版、通过企业审核、发布公告、撤回公告 | 强化平台端只做 SaaS 治理，不直接修改采购业务单据。 |

## 验收基线

阶段八每轮都必须保留阶段七的三端现场演示总验收包作为底线：

```bash
node scripts/stage-seven-onsite-demo-acceptance-check.mjs
npm run java:smoke
npm test
npm run build
```

其中三端现场演示总验收包必须继续满足：

- `totalActions = 17`
- `failedTotal = 0`
- 采购方 `failedCount = 0`
- 供应商 `failedCount = 0`
- 平台端 `failedCount = 0`

如果某轮只做文档或小范围前端提示，可以先跑定向测试、`npm run build` 和三端验收包；在收口前再跑全量 `npm test`。

## 阶段八不做清单

- 不做真实支付、税控开票、银行直连。
- 不做电子签章、法务模板库和合同生产级全生命周期。
- 不做 ERP、OA、财务系统深度集成。
- 不做商城直采、竞价采购、复杂招标、专家评审和保证金。
- 不做 AI 推荐、智能审批、支出分析和高级 BI。
- 不做套餐计费、用量统计、开放 API 和 Webhook。

这些能力不是不要，而是等现有三端演示链路具备稳定的产品观感后，再进入后续阶段。

## 决策标准

阶段八每一轮结束时只问三个问题：

1. 用户打开页面，是否比上一轮更容易理解业务状态？
2. 演示者点击关键动作，是否更容易说明结果和下一步？
3. 遇到不可操作或失败，页面是否能给出业务人员听得懂的解释？

三个问题都能回答“是”，这一轮才算真正推进了产品。
