# 项目分包、多采购执行与立项变更操作说明

后续执行收口批次已扩展未下发需求重编、受控终止、节点计划和整项目档案。关于“已有需求不能编辑或终止”的前批边界，以 `project-execution-closeout-guide.md` 的状态、权限和业务约束为准；不允许覆盖已下发执行或绕过订单履约。

## 使用入口与角色
采购方 → 项目库（?module=projects）。项目查看需要 buyer:project:read；管理需要 buyer:project:manage，同时受部门/本人数据范围约束。生成需求、询比、招标、履约和财务继续核验对应业务权限，不因项目管理权限自动开放。
立项变更在统一审批中心办理，业务类型为“立项变更”，管理员可在流程定义配置器发布独立流程，使用部门、金额及候选办理人配置。审批金额使用变更前后金额的较大值，不因调减申请绕过审批门槛。

## 一、批准项目拆分采购包
1. 打开已批准项目详情，进入“采购分包”，点击“新建分包”。
2. 填写包名称，按已批准物料分配数量。页面显示批准数量、已分配后的可用数量和参考单价，服务器校验总数量与预算，不能超分配。
3. 尚未分包、未采购的原项目关联需求可在新建时勾选纳入，不重复创建需求。已有包还可选择关联同部门、同年度的有效需求；需求数量和预算不得超过包范围。
4. 未关联需求、未下发采购的草稿包可编辑或取消。取消保留记录，不删除业务历史。已关联需求的包不支持直接取消或重写，避免断开已审批单据。
5. 每包先生成/关联需求，需求独立审批通过后，才可下发询比或招标。每个项目最多100包，列表10条分页；超限给出明确提示。

分币尾差：按批准金额分配；完整分配最后一包且单价未变化时，将四舍五入尾差显式计入最后一包，避免总额误差。包详情显示尾差，不静默增加预算。

## 二、多包独立采购与履约
- 一个项目可同时包含询比包和招标包；每包只有一条有效采购执行，业务链各自独立。
- 在分包详情查看需求、采购方式、有效执行、历史替换记录、履约和财务汇总，点击详情跳转对应源业务。
- 需求审批、供应商报价、评审定标、订单、合同、发货、收货、发票、付款仍在原业务模块办理。
- 需求进入预算占用；由该需求生成的订单沿用同一占用来源，不再重复占用。
- 仅无订单且已流标/废标的执行可重新采购。填写原因后创建新执行，旧执行标为已替换并保留，不覆盖报价、审批和失败原因。已有订单不得用重采绕开履约或财务责任。
- 原招标模块的独立重招入口不用于关联分包，应从分包“重新采购”入口操作，确保执行历史归属一致。

## 三、批准后变更
1. 已批准项目详情 → 立项变更 → 申请立项变更。
2. 填写变更原因，编辑项目基本信息、物料及预算单价/数量，上传变更证明。详情并列显示变更前、变更后方案。
3. 保存仅产生草稿，不改变已批准方案。项目同一时间只能有一条草稿或在审变更；变更台账按服务端分页，不受当前页影响判断。
4. 提交后进入真实 Flowable 流程。审批中冻结新增分包、生成/关联需求和新下发采购，已有订单履约可继续。
5. 审批通过才应用新项目方案；驳回、撤回不改变原方案。审批中心留存表单、处理人、意见、时间和附件。
6. 只允许调整尚未发出的剩余范围；已分配/已执行包的数量和预算不能被追溯削减。有业务关联后，部门和年度不能变更。
7. 保存草稿后项目内容如有更新，旧变更不能覆盖新基线，应撤回后重新发起，历史保留。
8. 新包绑定其创建时的批准方案版本和已批准变更。旧包和旧执行沿用原快照，不能因后续变更污染已归档凭证。

## 四、逐包和整项目结项
包级结项先核验实际订单、收货、发票、付款及合同归档，生成该执行的归档快照并结算预算余额。
整项目结项要求所有已批准明细有执行覆盖、无未处理变更、所有有效执行具备归档条件。汇总按有效执行去重，不累计已替换失败执行，不重复生成已有归档或释放预算。
ZIP包含对应采购执行资料、批准项目/分包快照、关联立项与变更审批历史及可访问原件。变更证明仅纳入绑定该变更版本的包，旧包不混入未来审批材料。

## 边界
本批沿用预算warning模式，不改为强拦截；预警不等于预算已实际拨付。付款登记不等于真实资金支付。
本批分包下发支持询比和招标；商城、竞价等已有独立模块不伪装成已接入分包。
跨年度资金结转、已下发包整体重构、已生成订单的采购终止清算、正式外部系统对接不在本批新增范围。
原单执行项目无需迁移：首次分包或变更时保存原执行基线，保留旧需求归属、旧归档和旧业务单据。
