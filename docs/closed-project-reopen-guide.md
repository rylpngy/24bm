# 已关闭项目与分包受控重开

## 业务范围

- 已结项或已终止项目须保留原立项批准记录，通过新的独立流程恢复办理权限；未批准就终止的草稿不能借此跳过立项。
- 可只恢复项目，也可同时明确选择一个已结项分包。项目仍有效时，可单独申请重开已结项分包。未选择的分包保持原状态。
- 不自动恢复终止需求、已取消分包、原合同或旧订单履约，不恢复库存，不重新发货或重复下单。终止分包的新增采购应按原批准范围新建分包承接。
- 重开不变更责任年度、原批准金额或资金来源。年度承接、立项变更及资金调整仍走独立业务。

## 操作步骤

1. 进入项目详情的“项目及分包受控重开”，点击“申请项目重开”或“申请分包重开”。
2. 选择范围，核对原责任年度、拟恢复的专项责任及各来源金额，填写原因。页面显示资金不足、在审业务、分包归属不符等具体限制。
3. 点击“提交重开审批”，填写已发布 `project_reopen` 流程的自定义表单，由配置的独立审批人办理。流程可在流程定义配置中设置节点、角色、人员和条件。
4. 申请中仍保持原关闭状态。发起人可以撤回本人申请，审批人可驳回；两者都不恢复预算责任、不改变原关闭状态。
5. 批准时重新核对项目、所选分包、真实付款、合同、履约、原档案和资金版本。发生变化需驳回后重提，不沿用过期依据。
6. 批准后项目为已批准，所选已结项分包恢复待办理状态，版本递增；其他分包、历史合同、需求、订单及现金不改写。
7. 如果涉及旧订单补充清算，仍须新的双方协议、供应商确认及独立清算审批，再登记真实退款/补付和最终凭证。正常履约且合同已归档的旧订单也须有对应分包重开授权，不能直接绕过归档限制。
8. 处理完成后重新核验并结项/终止。以后再重开需要新的申请和版本，不能重复使用旧批准记录。

## 预算与资金

已关闭专项项目只占用实际净付部分；重开项目会恢复原方案中已释放的未付责任。必须有足够的当前专项来源可用额度，审批时再次检查；预警模式不豁免专项来源额度约束。

若项目已恢复，只重开分包的恢复金额为零，不再占用一次项目资金。原资金版本、已付来源及跨年历史不重写，不能临时添加新来源。年度部门预算继续按真实需求和后续清算增量核验，不为重开伪造新需求占用；原 warning 默认模式保留，严格模式校验也保留。

## 档案与审计

项目重开前保存原关闭整项目 ZIP，按 SHA256 校验并只追加保存。重开申请详情和审批详情中的“下载原关闭档案”可下载该版本；同一关闭版本撤回、驳回后重提复用同一原件。只重开分包时继续使用原分包归档下载，不虚构新的整项目关闭档案。

原关闭档案缺失或失效且没有已保存的关闭版本时，须先在源采购中核验归档，不能推算或伪造原档案。整项目 ZIP 沿用 100MB 上限。

生命周期台账支持分页、撤回、审批历史和重开依据。采购执行新档案包含重开申请及其工作流证据；旧执行 ZIP 不覆盖。数据库拒绝没有独立批准的状态重开，并保护重开依据和原关闭 ZIP 不被修改、删除。

## 验收与发布

本地写入验收仅允许 API `127.0.0.1:8097`、采购方预览 `127.0.0.1:5201`。先准备上一批补偿清算完成、净付540元的隔离 `fundingUi` 场景，再执行：

```sh
ACCEPTANCE_LOCAL_WRITES=1 \
ACCEPTANCE_PASSWORD='<隔离验收密码>' \
PROJECT_REOPEN_FIXTURE='<基础场景报告>' \
PROJECT_REOPEN_CLEARING='<三版补偿清算完成报告>' \
ACCEPTANCE_REPORT_PATH='<本批结果JSON>' \
node scripts/closed-project-reopen-acceptance.mjs
```

脚本验证原关闭状态、撤回/驳回、实际页面选包提审、独立审批、660元专项责任恢复、补充清算至570元、再终止并恢复630元责任，以及原付款、旧清算和原关闭/分包 ZIP 不变。不得指向原系统，不执行真实银行或税务操作。开发、验收、CI、合并、部署分别记录，CI通过前不更新原系统。
