# 商城直采版 · 裸机走查手册

从**空数据库**开始,走完「开通 → 准入 → 上架审核 → 下单 → 履约 → 售后 → 评价 → 对账」的完整闭环。
部署与形态说明见 [商城直采版独立部署指南](mall-deployment.md)。

走查目的不是"点一遍都能点开",而是验证**该拒的确实拒得掉**。因此每一步都给了正例与反例,
反例是这份手册的重点——只走正路的走查证明不了任何事。

---

## 〇、起环境

```bash
cd infra && docker compose -f docker-compose.mall.yml --profile app --profile portals --profile admin up -d --build
```

| 端口 | 门户 | 走查角色 |
|---|---|---|
| 5174 | 平台运营端 | 平台管理员(仅开通阶段用) |
| 5173 | 采购方工作台 | 采购负责人 |
| 5175 | 供应商门户 | 供应商销售 |
| 5176 | 商城门户 | 采购方下单人 |

**走查前必须确认两件事**,否则会在第一步卡住:

1. **登录方式**。走查中新建的账号只存在于本系统(带密码),不在 Keycloak 里,
   所以门户镜像要用自研登录构建:`VITE_SELF_LOGIN=true docker compose ... up -d --build`,
   后端保持 `SELF_LOGIN_ENABLED=true`。
   **生产必须反过来**(两者都关,统一走 Keycloak)——这是走查环境的让步,不是推荐配置。
2. **平台管理员只能用 Keycloak 登录**。它在库里没有密码(`V172` 引导行密码列为空),
   在 5174 选 Keycloak 登录,账号 `platform.admin@example.com`,密码来自 realm 导入文件。

数据库是空的:没有租户、没有供应商、没有商品。下面每一条数据都由走查过程自己产生。

## 一、平台开通(5174,平台管理员)

### 1.1 新建采购企业租户

「租户列表 → 新建租户」。关键在**采购方式**一栏:**只勾「商城直采」**。

> **看什么**:这一栏就是"这个客户买了什么"。系统内置的采购方式可自由组合——
> 今天只勾商城,明天加勾询比,不需要换部署包、不需要迁移数据。

填管理员姓名、邮箱、密码——这是该企业的第一个账号,后续采购方操作都用它。

### 1.2 开通供应商企业

「企业审核 → 新建供应商企业」,同样填一个供应商管理员账号与密码。

> 供应商没有自助注册直通车。公开门户的入驻申请会进「待初审 → 初审通过 → 准入通过」
> 审核流,平台建档是干净环境下的引导入口。

---

## 二、采购方准备(5173,采购负责人)

登录后**先看左侧菜单**:

> **看什么**:应当**没有**「询比项目」「竞价采购」「招标管理」。
> 这不是前端藏起来了——1.1 只勾了商城直采,后端在立项入口按能力键放行,
> 绕过前端直接调接口同样会被拒。可在浏览器控制台验证:
> `fetch('/api/v1/buyer/rfqs')` 返回 404(部署形态关闭了整个接口面)。

### 2.1 物料目录

「物料目录 → 新建」建 2-3 个物料(如 A4 复印纸、签字笔)。
商品的名称与单位以采购方物料主数据为准,供应商只能定价,不能自造物料——避免同物异名。

### 2.2 供应商准入

「供应商库」找到 1.2 建的供应商,走准入,状态置为**已准入**。

> **反例**:先别准入,让供应商去上架(第三步),应当被拒:
> `仅可向已准入的采购方上架商品`。确认这条之后再回来准入。

---

## 三、供应商上架(5175,供应商销售)

### 3.1 建商品与规格

「商城货架 → 发布商品」:选采购方、选物料、填协议价与单位。

保存后回列表,该行状态是 **待审核**,操作列是 **待采购方审核**(不可点)。

> **看什么**:供应商**不能自己把商品放上货架**。能自己上架的话,审核就形同虚设。
> 供应商能做的只有「提交审核」与「下架」。

多规格商品走「编辑」页加规格:每个规格有自己的**起订量 / 递增步长 / 库存 / 交期 / 阶梯价**。

> **反例**(值得逐条试):
> - 阶梯价第二档单价高于第一档 → `阶梯价需随数量递减`(不递减的阶梯没有意义)
> - 起订量或步长填 0 → 被拒
> - 商品一个规格都没有就提交审核 → 被拒

### 3.2 提交审核

草稿或被驳回的商品,列表操作列是 **提交审核**。点它,状态转 **待审核**,采购方收到站内通知。

---

## 四、采购方审核(5173)

「企业商城 → 上架审核」,页签上带**待审数量角标**。

| 操作 | 预期 |
|---|---|
| 不写意见直接通过 | 被拒:`审核意见不能为空(留痕要求)` |
| 驳回 + 写意见 | 商品退回**草稿**,供应商收到通知与意见,可补正后重新提交 |
| 通过 + 写意见 | 商品转**在架**,商城门户立即可见 |

> **看什么**:**通过也要写意见**,不只是驳回要写。审核意见与时间落库留痕,
> 事后要能回答"这个商品当初是谁、凭什么放进货架的"。

审核通过后回供应商端看:该行状态变 **在架**,操作列恢复为 **下架** 开关——
上下架的日常管理权重新回到供应商手里,但**重新过审这件事只发生一次**。

---

## 五、商城门户下单(5176)

用 1.1 建的采购方账号登录。未登录时能看到的是**公开专区**,私域协议价商品必须登录后可见。

### 5.1 浏览与详情

首页 → 分类 → 商品详情。详情页调数量,观察:

> **看什么**:数量跨过阶梯档位时**单价与小计实时变化**。
> 价格由服务端重算,前端只是显示——购物车里改数字改不了成交价。

### 5.2 加购与校验(反例集中在这里)

| 操作 | 预期 |
|---|---|
| 数量低于起订量 | `低于起订量:本规格起订 N 件` |
| 数量不是步长整数倍 | `数量需按 N 件的整数倍递增` |
| 数量超过库存 | `库存不足:仅剩 N 件` |
| 加购后供应商把商品下架,再回购物车 | 该行标出不可下单原因,结算被拦 |

最后一条是重点:**购物车只存"规格 + 数量"**,单价、可售性都在渲染时实时重算。
把单价存进购物车的做法,会让昨天加购的东西按昨天的价格结算。

### 5.3 结算

填收货地址(可存入地址簿复用)与期望到货日,提交。

> **看什么**:多供应商的购物车会**按供应商拆成多张订单**——履约与对账的对象是供应商,
> 一张跨供应商的订单没法发货也没法对账。交期取各规格交期的**最大值**。

下单后「我的订单」立刻能看到新订单(列表按创建时间倒序)。

## 六、履约

| 角色 | 位置 | 操作 |
|---|---|---|
| 供应商 | 5175「销售订单」 | 确认订单 → 发货(填物流) |
| 采购方 | 5173「收货验收」 | 登记收货与验收 |

订单状态链:`待供应商确认 → 已确认 → 已发货 → 已收货`。

---

## 七、售后(订单行级)

### 7.1 采购方申请(5176「我的订单」,展开订单行)

选类型(退货 / 换货 / 维修)、填数量与原因。

> **看什么**:售后挂在**订单行**上,不是整张订单。一张订单里只有某一行有问题是常态。

| 反例 | 预期 |
|---|---|
| 订单还没发货就申请 | `售后须在发货后申请` |
| 类型填「退款」 | `售后类型须为 退货 / 换货 / 维修` |
| 数量超过该行订购数 | `售后数量超过订购数量:本行共 N` |
| 原因留空 | 被拒 |

### 7.2 供应商处理(5175「商城货架」页顶部售后待办区)

> **看什么**:待办区**只在有待处理/处理中的单子时出现**,没有待办就不占版面。

| 操作 | 预期 |
|---|---|
| 拒绝但不填理由 | `拒绝售后必须说明理由` |
| 完成 / 拒绝(带理由) | 采购方收到站内通知与回复 |
| 已完成的单再处理一次 | `该售后单已结束(已完成),不可重复处理` |

采购方也可在 5173「企业商城 → 售后处理」页签查看本企业全部售后单。

---

## 八、评价

5176「我的订单」,已收货的订单行可打 1-5 星 + 文字。

| 反例 | 预期 |
|---|---|
| 未收货就评价 | `评价须在收货后提交` |
| 同一订单行评第二次 | `该订单行已评价过,不可重复评价` |

> **看什么**:一行一次的限制在**库上有唯一约束**,应用层也拦一道。
> 只靠前端禁用按钮的评价体系,刷分只是时间问题。

商品详情页可看到该商品的历史评价。

---

## 九、发票与对账(5173)

「发票付款」:供应商开票 → 采购方核对 → 付款。对账走订单-发票-收货三单匹配,差异单独成页。

## 十、形态边界复核

走查最后确认这一版**卖的是什么**:

| 检查 | 预期 |
|---|---|
| 采购方菜单 | 无询比 / 竞价 / 招标 |
| 直接请求 `/api/v1/buyer/rfqs` | 404 `本部署为商城直采版,未开放该功能接口。` |
| 直接请求 `/api/v1/buyer/tenders` | 同上 |
| 商城、订单、发票、售后接口 | 正常 |

> **两层开关的区别**(客户会问):
> **部署形态**关的是"这套部署卖的是什么"(接口面 404);
> **租户能力**关的是"这个租户买了什么"(立项入口按方式拒绝)。
> 两层防的不是同一件事,所以都要有。
>
> **如实说明的边界**:形态开关裁的是 **HTTP 接口面,不是 Bean 装配**——
> 相关服务仍在容器里(商城下单内部要调用寻源上下文的锚点服务),
> 内存占用与完整版一致。对外能力边界以 `DeploymentSurfaceFilter.NON_MALL_PREFIXES` 为准,
> 新增寻源/招标控制器时需手工同步该清单。
