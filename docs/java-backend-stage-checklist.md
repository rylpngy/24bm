# Java 后端阶段性检查清单

本文档用于记录当前 Java 后端 MVP 主链路已经落地的状态机、唯一性约束和后续迭代入口。它不是产品需求全集，而是后续继续扩展审批流、对账和三单匹配时的回归检查基线。

## 当前主链路

采购履约与财务闭环当前固定为：

```text
待供应商确认 -> 待发货 -> 已发货 -> 已收货 -> 待付款 -> 部分付款/已付款
```

订单履约由 `purchase_orders` 驱动，供应商确认、发货、采购方收货、供应商开票和采购方登记付款都必须从当前 JWT 身份上下文解析租户或供应商范围。

## 履约约束

- 供应商确认订单前，订单必须属于当前 `supplierId`，且状态必须是 `待供应商确认`。
- 发货前，订单必须属于当前 `supplierId`，所属采购方租户必须启用 `order` 功能，且订单状态必须是 `待发货`。
- 同一采购订单只能登记一条发货记录，服务层通过 `deliveries` 计数拦截，数据库通过 `tenant_id + order_id` 唯一约束兜底。
- 收货前，订单必须属于当前采购方 `tenantId`，当前租户必须启用 `order` 功能，且订单状态必须是 `已发货`。
- 收货前，当前租户下该订单必须存在状态为 `已发货` 的发货记录，避免仅凭订单状态绕过发货事实。
- 同一采购订单只能登记一条收货记录，服务层通过 `receipts` 计数拦截，数据库通过 `tenant_id + order_id` 唯一约束兜底。

## 发票与付款约束

- 供应商登记发票前，订单必须属于当前 `supplierId`，订单状态必须是 `已收货`，且订单所属采购方租户必须启用 `finance` 功能。
- 发票金额必须等于采购订单金额，作为三单匹配前的基础金额一致性校验。
- 同一采购订单只能登记一张发票，服务层通过 `invoices` 计数拦截，数据库通过 `tenant_id + order_id` 唯一约束兜底。
- 新发票初始付款状态固定为 `待付款`。
- 付款登记前，发票必须属于当前采购方 `tenantId`，当前租户必须启用 `finance` 功能。
- 付款登记前会重新校验发票金额仍等于采购订单金额，防止绕过发票创建入口或中途数据漂移。
- 付款登记前会校验发票供应商在当前采购方私域供应商关系中不能是 `黑名单`。
- 付款状态当前只允许从 `待付款` 更新为 `部分付款` 或 `已付款`。

## 数据库兜底

当前已经在初始 Flyway schema 中对这些“一单一节点”关系做唯一约束：

- `deliveries`: `unique (tenant_id, order_id)`
- `receipts`: `unique (tenant_id, order_id)`
- `invoices`: `unique (tenant_id, order_id)`

这些约束和服务层校验同时存在：服务层负责给出业务错误，数据库约束负责兜住并发和绕过服务层的异常写入。

## 审计与通知

- 供应商确认订单记录 `purchase_order.confirmed`。
- 供应商发货记录 `purchase_order.shipped`，并给当前采购方租户 active 用户发送站内通知。
- 采购方收货记录 `purchase_order.received`，并给当前采购方租户 active 用户发送站内通知。
- 供应商登记发票记录 `invoice.created`。
- 采购方登记付款记录 `invoice.paid` 或 `invoice.partial_paid`。

## 后续迭代入口

- 三单匹配：在当前订单金额、收货事实和发票金额一致性基础上，扩展为订单、收货、发票三方明细级匹配。
- 对账：引入对账单、应付/应收和逾期提醒，避免仅靠发票付款状态表达财务进度。
- 分批履约：如果后续要支持分批发货、分批收货和分批开票，需要拆分当前“一单一节点”约束，引入明细行、批次、累计数量和累计金额校验。
- 审批流：将付款、异常收货、超额开票等动作接入可配置审批模板。
- 风控与绩效：沉淀供应商准时发货、验收结果、付款异常和黑名单状态，用于供应商绩效评分与风险预警。
